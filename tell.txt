# tell.txt — what was done, what to adjust, what could be better

Project: IEEE community portal (`C:\Users\HP\OneDrive\Desktop\ieee form`)
Stack: Next.js 14 (App Router, TypeScript) + Prisma on Neon Postgres + Firebase email-link auth.

---

## 1. What is done (verified)

### Quiz system (from the earlier round, still working)
- Manager creates / edits / publishes / deletes quizzes with three question types:
  `OBJECTIVE` (single correct option), `SHORT_TEXT` and `LONG_TEXT` (manager supplies accepted answers).
- Participant area at `/quiz` lists only the quizzes of their own learning track, one attempt per quiz
  (enforced by a unique index on `(quizId, participantEmail)`, plus a `P2002` fallback in the submit route).
- Manager results panel shows every attempt with per-question responses, points and correct answers.
- Registration management (search, filters, pagination, edit, delete, CSV-style review) is complete.

### 1.1 Every alert / confirm / prompt is now a modal
- New `components/use-modal.tsx` exposes `showAlert(title, message, tone)`,
  `confirm(...)` and `prompt(...)`, returning promises, and renders one Radix `AlertDialog` stack.
- All native dialogs are gone — verified by grep: `window.alert`, `window.confirm` and `window.prompt`
  no longer appear anywhere in `app/` or `components/`.
- Converted call sites: `register-form.tsx`, `admin-dashboard.tsx` (remove manager / delete track now show
  what exactly is deleted), `registrations-manager.tsx` (delete participant), `quiz-manager.tsx`
  (delete quiz), and `auth-sign-in.tsx` (magic-link email confirmation on a different device).
- Alerts are toned: `success` / `error` / `info`, so a failure no longer looks like a neutral notice.
- The old `components/use-alert.tsx` was deleted because nothing referenced it anymore.

### 1.2 SHORT_TEXT is graded by the AI model (embeddings removed)
- Embedding similarity was **removed** from grading. Cosine similarity between the answer and the accepted
  answers was giving ~0.69 to a correct-but-wordy answer and, worse, treated topically close but factually
  wrong answers as nearly right, so it over-rewarded inaccuracies.
- `lib/nvidia.ts` now calls `https://integrate.api.nvidia.com/v1/chat/completions` for **both** written
  question types. For `SHORT_TEXT` the model is told to read the question and grade strictly: accept only
  factually correct, complete answers (case, punctuation, synonyms, abbreviations and correct alternative
  names are fine), score 0 for wrong / off-topic / nonsense answers, and never above 0.5 when the answer
  contains a factual error.
- The manager's accepted answers are the rubric. Anything the model does not agree with is recorded as a
  reason, so the manager can see exactly why an answer scored what it scored.
- **Fallback is exact comparison, not embeddings.** An exact or keyword match against an accepted answer is
  full credit without an AI call. If the API call fails, times out, rate-limits or returns unusable JSON,
  that question is graded purely by the deterministic exact/keyword comparison — it either matches an
  accepted answer or it does not.
- `temperature` is 0 for deterministic grading, and each call is retried up to 3 times with backoff on
  network errors, 429 and 5xx responses before the fallback kicks in.
- Verified live: "A stack, because it removes the most recently added item first" → full credit;
  "a queue, which also handles priority" → not correct, 0/3; "443" → exact match; an off-topic long answer → 0/5.

### 1.3 LONG_TEXT is graded by the same model
- `lib/nvidia.ts` asks the model to compare the participant's answer with the manager's accepted answers and
  reply with JSON `{ "score": 0..1, "reason": "..." }`, judging correctness, completeness and whether it
  covers what the question asked, and giving no credit for unsupported claims.
- The awarded fraction, the reason and the model name are stored per answer
  (`aiScore`, `aiReason`, `aiModel`, `gradedBy = "AI"`), and shown to the manager and to the participant.
- Model and key are configurable through `.env`; no code change needed.

### 1.4 Participants and managers can answer with a PDF (Cloudinary)
- Cloudinary stores the documents (`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`,
  `CLOUDINARY_UPLOAD_FOLDER` in `.env`). The **API secret never reaches the browser**: files are posted to
  `POST /api/uploads/pdf`, the server signs and forwards them, and the route answers with the Cloudinary
  link plus the text it extracted from the document. Uploads are limited to 40/hour per user in process,
  10MB, and `MAX_PDF_PAGES` pages (default **25**) — over that the request is rejected with 422 before
  anything is stored.
- `lib/pdf.ts` extracts the text per page with `unpdf` (added as a dependency and kept outside the server
  bundle through `next.config.mjs`). Only the first `MAX_PDF_PAGES` pages and `MAX_PDF_CHARS` characters
  (default 60000) are analysed, and a PDF with no selectable text is rejected with a clear message instead
  of being graded as a blank answer. Scanned documents need OCR first.
- **Manager reference PDF:** every subjective question in the editor has an *Attach PDF* button. The text is
  stored on the question (`referenceFileUrl`, `referenceFilePages`, `referenceFileText`) and given to the
  model as extra context while the accepted answers stay the rubric. Participants see the link so they know
  which document the question is about.
- **Participant answer PDF:** every written question has an *Upload PDF* option next to the text box. The
  extracted text is what gets graded (`responseFileUrl`, `responseFilePages`), stored so the manager can
  read the answer, and the participant gets a link to their own file on the published result.
- Verified live: a 2-page PDF describing photosynthesis, submitted as the only answer to a 5-point
  long-answer question, was extracted and graded 5/5 by the model with a reason; the same question with a
  foreign reference link stored no context; a 40-page PDF was rejected with 422; a text file with a `.txt`
  name was rejected with 415; anonymous uploads were rejected with 401.

### 1.5 Cloudinary delivery on this account needs signed URLs
- Public delivery of newly uploaded PDFs answers **401** on cloud `sx1dtsdq` (older image assets still
  deliver normally), and neither HTTP Basic auth nor the documented delivery signatures were accepted, so
  extraction cannot depend on downloading the file again.
- Therefore the text extracted **during upload** is what gets stored and graded, and the server only falls
  back to downloading from Cloudinary when no text was supplied. Only URLs on our own cloud are accepted,
  so a payload cannot make the server fetch an arbitrary file.
- Consequence to keep in mind: the PDF text travels from the upload response to the save/submit request, so
  a determined participant could submit text that does not match their file. It only affects their own
  grade, the manager still sees the PDF link and the stored text, and the manager can override the score.
  If delivery is enabled for the cloud later, the server-side download path takes over automatically.

### 1.6 Scores stay private until a manager publishes them
- New `QuizAttempt.resultStatus` (`PENDING_REVIEW` → `PUBLISHED`), plus `publishedAt`, `publishedBy`,
  `adjustedScore`, `adjustedMaxScore` and `adjustedFeedback`.
- Submitting stores the automatically graded score immediately (so nothing is lost) but returns only a
  "pending" payload: no score, no correct answers, no AI verdicts.
- `GET /api/quizzes/{id}/take` and `GET /api/quizzes/available` also keep the score hidden while pending.
- New `POST /api/quizzes/{id}/publish` (approve, optional score override + note) and
  `DELETE /api/quizzes/{id}/publish` (withdraw back to review). Admin or the track's manager only;
  participants get 403.
- Manager UI: each attempt shows *Awaiting review* or *Published*, the AI breakdown per question,
  an optional score override and note, and Publish / Withdraw buttons.
- Participant UI: `/quiz/{id}` shows an explicit "awaiting review" card with no numbers, then the graded
  result (score, percentage, per-question AI feedback) once it is published.

### 1.7 Other fixes found while testing
- `submit/route.ts` exported a helper, which Next.js rejects for route files
  (`Type ... does not satisfy the constraint { [x: string]: never }`). Moved to `participantResult()` in `lib/quiz.ts`.
- Neon driver crash `TypeError: bufferUtil.mask is not a function`: the `ws` package was being pulled into the
  server bundle. Fixed by using the runtime's global `WebSocket` and keeping `ws` as a fallback for older Node,
  with `serverComponentsExternalPackages: ["ws", "@neondatabase/serverless", "unpdf"]` in `next.config.mjs`.
- Stale `next dev` processes were holding port 3010 and serving old bundled code, which made the fix look
  unreliable. Clean process restarts are now required after `next.config.mjs` changes.

## 2. What you may need to adjust

1. **Rotate the exposed credentials.** The NVIDIA API keys, the Cloudinary API key/secret and the database
   connection string were pasted into chat. They live only in `.env` (git-ignored) and no code contains them,
   but they should be considered compromised. Create a new NVIDIA key pair, rotate the Cloudinary API secret
   and rotate the Neon credential.
2. **Only one NVIDIA key is needed now.** `NVIDIA_CHAT_KEY` is the only key the app reads, because grading no
   longer uses embeddings. The separate `NVIDIA_EMBED_KEY` and `NVIDIA_EMBED_MODEL` were removed from `.env`
   and `.env.example` (the embeddings key also returned HTTP 403). `NVIDIA_SIMILARITY_THRESHOLD` and
   `NVIDIA_SIMILARITY_FLOOR` are gone as well, since there is no similarity mapping left.
3. **The chat model was changed.** `google/diffusiongemma-26b-a4b-it` answers with HTTP 200 and an empty
   message, so it cannot be used for grading. The default is now `nvidia/nemotron-3-super-120b-a12b`,
   which returns clean JSON. Set `NVIDIA_CHAT_MODEL` if you prefer another model.
4. **Grading strictness is prompt-driven.** `SHORT_TEXT` is graded by the model with explicit instructions to
   reject factually wrong answers, which fixed the over-generous scoring, but the model can still be lenient on
   unusual phrasings. Review the reason text on the first few attempts and tighten the instructions in
   `gradeWrittenAnswer()` in `lib/nvidia.ts` if you see something you disagree with. Managers can override
   any single attempt before publishing.
5. **Database schema has no migration folder.** The new columns and enums
   (`ResultStatus`, `GradingMethod`, `resultStatus`, `publishedAt`, `publishedBy`, `adjustedScore`,
   `adjustedMaxScore`, `adjustedFeedback`, `gradedBy`, `similarity`, `aiScore`, `aiReason`, `aiModel`,
   `Question.referenceFileUrl`, `Question.referenceFilePages`, `Question.referenceFileText`,
   `AttemptAnswer.responseFileUrl`, `AttemptAnswer.responseFilePages`)
   were applied to the live database with direct SQL, because `prisma db push` cannot open direct TCP to Neon
   from this network. On a fresh database you must run the equivalent SQL or generate a migration by hand.
6. **Node.js 22+ is required** for the Neon WebSocket driver path (global `WebSocket`). Older runtimes fall
   back to the `ws` package, which needs to stay outside the server bundle.
7. **Submit latency.** Long answers are graded sequentially, so a quiz with many written answers can take
   30-120 seconds. `maxDuration = 120` is set on the submit route; if quizzes grow large, batch the calls or
   move grading to a background job.
8. **Firebase headers.** API routes trust the `X-User-Email` header, because the Firebase session token is not
   verified server-side. This is fine for the current deployment, but anyone who can send that header could
   read data. Verify the ID token before going public.
9. **PDF limits are environment variables.** `MAX_PDF_PAGES` (25), `MAX_PDF_BYTES` (10MB) and `MAX_PDF_CHARS`
   (60000) decide how much of a document the model reads. 25 pages of dense prose is roughly 12-15k tokens,
   which the current model handles comfortably. Raise `MAX_PDF_PAGES` only if the model context allows it.
10. **Cloudinary delivery settings.** The links shown in the UI only open while the cloud allows public
    delivery for PDFs. On this account they currently answer 401, so the links will not open until delivery is
    enabled (or the assets are made publicly readable). Grading is unaffected — it uses the text extracted
    during upload.

## 3. What could be better

- **Verify the Firebase token server-side** instead of trusting the email header, and use the email from the
  verified token rather than from the request.
- **Re-verify PDF text server-side.** Because delivery is restricted, the extracted text travels from the
  upload response to the save/submit request. Signing the text (or hashing the file and re-extracting once
  delivery works) would remove the possibility of a participant grading a document they never uploaded.
- **Delete orphaned PDFs.** Removing a question or a quiz leaves its Cloudinary file behind. A cleanup job
  (or deleting the asset in the quiz/question DELETE routes) would keep the media library tidy.
- **Grade all written answers in one model call.** Sending every short and long answer in a single request
  would cut latency, cost and the number of chances for a transient API failure.
- **Make the manager's answer a rubric with levels** (for example "full / partial / incorrect" with point
  ranges) instead of free text, so LLM grading is more consistent and easier to audit.
- **Add an attempt review history.** Publishing records who published and when, but there is no audit trail
  of score overrides. A `QuizAttemptEvent` table would make disputes traceable.
- **Support retakes.** Right now the unique index makes an attempt permanent. An admin-only "clear attempt"
  action would be useful when a participant loses internet mid-quiz.
- **Notify participants** by email when a result is published, instead of making them refresh the page.
- **Move the manual DDL into a migration file** and add a CI check, so a new environment cannot silently
  miss these columns.
- **Add unit tests** for `lib/quiz.ts` (answer normalisation, keyword matching, exact-match fallback)
  and for the publish/withdraw permission rules. Today they are covered by the live smoke test only.
